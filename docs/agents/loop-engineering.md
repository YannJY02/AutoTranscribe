# Matt Workflow Loop Engineering

Status: current
Mode: sequential safe

This is the operating standard for using Matt workflow skills in this repo. It turns each development pass into a bounded loop with explicit context, action, verification, feedback, and record keeping.

## Purpose

Use this standard when work should make InsightKit easier for future agents to operate, not only when shipping a feature. The expected result of each loop is a small verified change plus an updated local issue or handoff surface.

## Preconditions

- Start from `AGENTS.md`.
- Read `docs/agents/issue-tracker.md`, `docs/agents/triage-labels.md`, and `docs/agents/domain.md`.
- Read `CONTEXT-MAP.md`, then only the context-specific `CONTEXT.md` files relevant to the loop.
- Read accepted ADRs under `docs/adr/` before proposing module changes.
- Use `.scratch/<feature>/PRD.md` and `.scratch/<feature>/issues/<NN>-<slug>.md` for PRDs and issues.

## Standard Loop Packet

Every loop should be expressible in this packet before implementation starts:

1. Goal: the concrete repo or software state that will be true when the loop ends.
2. Context: the context docs, ADRs, source files, proof artifacts, and local issues being used as authority.
3. Boundary: what is in scope, what is out of scope, and what requires stopping to ask.
4. Action: the smallest implementation or documentation change that can satisfy the goal.
5. Verification: commands, proof files, or manual checks that must pass.
6. Feedback: the next action if verification fails.
7. Record: where the result, proof path, decision, or follow-up issue is written.

## Matt Workflow Routes

### Project Health Route

Use this route for architecture and codebase health work:

1. `review`: inspect the current diff and identify risks before adding more changes.
2. `improve-codebase-architecture`: generate deepening candidates from context docs, ADRs, and code friction.
3. `grilling` plus `domain-modeling`: sharpen the chosen module, interface, and domain vocabulary.
4. `to-prd`: turn the accepted design into a bounded PRD under `.scratch/<feature>/PRD.md`.
5. `to-issues`: split the PRD into independently verifiable issues under `.scratch/<feature>/issues/`.
6. `implement`: work one issue at a time in a fresh context window when the issue is ready.

### Feature Route

Use this route when the user has a new product or workflow idea:

1. `grill-with-docs`: sharpen the idea while preserving repo context.
2. `to-prd`: write the feature PRD.
3. `to-issues`: split into implementation slices.
4. `implement`: execute one issue at a time.

### Incoming Issue Route

Use this route for raw bug reports or requests that were not generated by `to-issues`:

1. `triage`: classify the issue using the labels in `docs/agents/triage-labels.md`.
2. `implement`: pick only issues that are `ready-for-agent`.

Do not triage issues already generated by `to-issues`; they should already be specified enough to implement.

### Legacy Asset Promotion Route

Use this route when moved historical material needs to become useful current workflow material:

1. Start at `docs/Legacy/matt-workflow-library/manifest.md`.
2. Read the converted asset before the original file; the converted asset explains the current authority boundary.
3. Check current code, context docs, ADRs, and proof before asking the user whether the historical item is still useful.
4. Classify the item as one of: context term, ADR candidate, current PRD or issue, proof or release evidence, owner input, or Legacy reference.
5. Promote only unfinished useful work into `.scratch/<feature>/`; do not treat historical issue-style files as active issues by themselves.
6. Verify the result with `python3 scripts/verify_project_normalization.py` and record the proof path.

## Verification Ladder

Apply the ladder from weakest to strongest. A loop is not complete at `Exists` unless the loop goal only required an asset to exist.

| Level | Question | InsightKit examples |
| --- | --- | --- |
| Exists | Does the artifact exist? | `docs/agents/loop-engineering.md` exists. |
| Contains | Does it contain the required sections or terms? | The loop standard names Goal, Context, Boundary, Action, Verification, Feedback, and Record. |
| Matches | Does it match repo conventions? | The route uses local markdown issues and multi-context docs. |
| Works | Does executable verification pass? | `python3 scripts/verify_project_normalization.py` and pytest pass. |
| Explains | Can a future agent tell what to do next? | The route identifies which Matt skill to use and when to stop. |
| Records | Is the outcome written to the right ledger, issue, proof, ADR, or context doc? | The local issue comment names the proof path and remaining blockers. |

## Required Gates

Run the narrowest gate that supports the claim, then broaden when the change touches shared behavior.

| Claim | Gate |
| --- | --- |
| Matt workflow assets are structurally valid | `python3 scripts/verify_project_normalization.py` |
| Legacy workflow assets are moved, classified, and linked into current rules | `python3 scripts/verify_project_normalization.py` |
| Python runtime behavior still works | `PYTHONPATH=. python3.11 -m pytest -q --tb=short` or the local Python equivalent |
| Release wording or local release readiness changed | `python3 scripts/verify_release_closure.py` |
| Installed app behavior changed | packaged-app smoke and, when UI behavior changed, Visual GUI Proof |
| Swift/macOS module behavior changed | targeted `swift test --package-path macos/InsightKitApp --filter <TestName>` before broader checks |

## Feedback Packet

When verification fails, write the feedback in this shape before continuing:

- Evidence: the exact failing command, proof path, assertion, or observed behavior.
- Gap: what the current artifact or code does not prove.
- Constraint: the ADR, context term, external blocker, credential limit, or blast-radius limit.
- Next action: the smallest change that could close the gap.
- Recheck: the exact command or proof that will be rerun.
- Stop rule: the condition that requires asking the user instead of continuing.

## Stop Rules

Stop and ask before:

- using credentials, API keys, Apple account actions, certificates, notarization, App Store Connect, or public privacy URL decisions;
- rewriting accepted ADRs or replacing native macOS shell, Python Sidecar, or Unix socket RPC architecture;
- deleting records, logs, proof artifacts, or user-owned data;
- broad refactors that are not tied to a local PRD and issue;
- claiming Distribution Ready when only Local Release Ready evidence exists.

## Record Keeping

At the end of a loop:

- update the relevant `.scratch/<feature>/issues/<NN>-<slug>.md` comment section with status and proof paths;
- update `CONTEXT.md` only when domain vocabulary changed;
- add an ADR only for hard-to-reverse decisions with real alternatives;
- keep generated proof under `logs/diagnostics/<date>/`;
- leave external blockers as `External Blocker` or `Owner-Controlled Input`, not failed code work.
